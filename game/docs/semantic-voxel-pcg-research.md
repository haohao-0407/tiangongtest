# 由粗体素节点驱动的结构级 PCG

2026-11-14，依据用户补充的建筑/道路参考图修正方案。本文件取代上一版“表面微体素细化”作为主方案；旧报告中的网格合并、AO、缓存仍可用于输出阶段。

状态：一手资料调研、当前项目只读核查与独立交互示意。未接入游戏运行时，未实测游戏性能。

## 1. 目标与技术选择

目标是编辑低分辨率地图节点后，系统根据用途、邻接、高度和周边空间，自动生成新的结构：墙面形成窗洞、窗框、外凸窗台、檐口；道路形成连续铺面、边缘人行道、路沿和合适的高差连接。

推荐 **语义粗格图 + 邻接自动拼装（Autotiling / Dual Grid）+ 上下文敏感形状语法（Context-Sensitive Shape Grammar）**。这是针对本工程组合的架构，而不是一个可以直接安装的现成 ForgeAX 包。

每个原体素是控制节点，但生成对象可以归属于一条边、一组节点、一整段立面或一个交叉口。16×16×16 是最终几何分辨率：1 个原格对应 16 个微格的边长。窗台可以伸出原格，雨棚可以跨多格，楼梯可沿几格延伸；不能把输出限制在各自独立的 16³ 盒子内。

参考图可观察到重复的窗列、窗框与窗台、连续檐口、入口与平台、道路边界等层次。这些是结构规则的设计目标；单张参考图不能证明其原游戏使用了哪种 PCG 算法。

前轮 MarkovJunior 仍可用于多阶段重写/模块生成，但“把粗格放大”本身不是这一轮的核心。WFC 可在合适的区域选择窗型、屋顶或装饰组合；入口、道路和结构的确定性规则应先成立。也不必引入自动学习图语法或神经网络来开始实现。

## 3. 从节点到结构的分层

```text
粗地图 / 建筑节点 / 用途标记 / 用户少量覆盖
    ↓
邻接图：相连、朝向、内外侧、上下关系、高度差
    ↓
结构提取：连续墙面、立面窗间、道路区域、外边界、路口
    ↓
规则：分段、重复、预留、开洞、挤出、沿边铺设、收口
    ↓
结构特征：窗洞+窗框+窗台，檐口，人行道，楼梯等
    ↓
跨格占据/避让与通行校验
    ↓
按 1/16 世界单位生成模块或栅格化 → 合并网格 / 碰撞与导航
```

### 节点、边和连续区域各自负责什么

| 层级 | 典型输入 | 生成职责 |
|---|---|---|
| 单节点 | 墙、道路、草地；材质；高度；样式 | 提供用途和局部候选，不独立决定完整立面 |
| 共享边/角 | Road–Grass、Road–Road、墙角、坡差 | 路沿、侧边铺面、转角收口、台阶连接候选 |
| 连续区域 | 一整段墙、同一建筑、道路区域/交叉口 | 窗距、楼层、入口、檐口连续性、路口融合 |
| 派生 Feature | 一个窗口、雨棚、一段路沿、一段楼梯 | 拥有稳定 ID、占据范围、依赖节点和几何输出 |

这允许“每格是节点”，同时让有跨度的结构保持完整。Road–Road 的内部共享边不产生路沿，墙角不由相邻两格各自重复生成柱子。

## 4. 墙面如何自动生成窗台等部件

建议流程：

1. 从同建筑、同朝向的暴露墙面提取连续 `FacadeRun`。读取墙高、宽度、楼层基准、入口、内部房间、前方空间与样式。
2. 先分出墙脚、窗带和顶端檐口，再根据可用宽度安排若干完整窗间。转角保留实体墙柱，入口占据优先。
3. 对每个可开窗的窗间生成一个 `WindowFeature`：开洞范围、玻璃/暗内腔、窗框、窗台、窗楣，以及可选花箱/遮阳。
4. 窗台沿立面法线向外挤出，可跨原格边界；检查其体积是否碰到邻墙、入口通道或其他关键结构。
5. 多格檐口作为连续带生成，在端点和转角收口。上方新增墙后，旧顶沿不再是顶部，自动移除或转为楼层腰线。

概念规则（自定义伪语法，不是现有引擎 API）：

```text
FacadeRun -> BaseBand + RepeatedWindowBays + Cornice
WindowBay [enoughSpace && openingAllowed && exteriorClear]
          -> CarveOpening + Frame + Glass + ExtrudedSill + Lintel
WindowBay [otherwise] -> SolidWallPanel
EntryBay  -> DoorOpening + Canopy? + Landing + HeightConnection?
```

“自动”仍需要建筑样式定义窗距、窗台高、边柱宽、开口比例等。可允许 `opening=auto/solid/window/door` 覆盖规则，以防重要墙面或玩家意图被自动开洞。孤立墙段与室内隔墙不能仅凭石材自动认定为建筑正立面。

视觉窗口不要求成为可行走通道，但真正的门洞、平台、楼梯会影响通行，必须与逻辑占据、碰撞和寻路一致。不能一律按上一版的纯显示层处理。

## 5. 道路、人行道和台阶如何联动

### 同高度的道路

先把道路节点合成路面区域，再提取区域边界。共享内部边去掉；只沿外边界应用道路样式截面，如“路面→路沿→人行道→草地”。

| 邻接或编辑 | 建议响应 |
|---|---|
| 道路与道路同高相邻 | 路面合并，内部不生成路沿 |
| 道路与可占用草地相邻 | 按道路样式生成边缘铺面、路沿和人行道 |
| 新增支路形成 T/十字路口 | 去掉接入口原路沿，融合路面，人行道沿新的外边界转弯 |
| 道路末端 | 使用端头/封边模块，若接入口则保持贯通 |
| 人行道接建筑入口 | 留通道、调整路沿，生成门前平台或高度连接 |
| 邻侧是建筑、河流或保留地 | 使用避让/挡墙/护栏等对应规则，不能强行覆盖 |

人行道可以占道路原格内部的一条边带，也可以使用邻接空地；样式必须明确其宽度与允许的扩张范围。宽阔的可行走人行道通常需要实际空间预留，不能任意侵占建筑。

### 有高差时

路沿和楼梯是不同结构。只有两个允许连接的步行表面存在高差，且有足够水平长度和净空时，才产生楼梯。车辆道路与步行路径应使用不同坡度/高差规则。

例如，若原格代表 1 世界单位，高差 1 格即 16 微格；选择每级升高 2 微格，需要 8 级。若每级进深 3 微格，就需要 24 微格、即 1.5 原格的水平展开空间（这是设计示例，并非建筑规范）。空间不足时应保留明确边界，或在更大范围规划连接，不能把八级楼梯硬塞进一个 16³ 单元。

台阶生成后输出踏面/坡面高度查询或合适的碰撞体，并把连接信息交给导航。原来的“可跨一格高差”判定不等于角色已经能沿细台阶平滑运动。

### 自动拼装的具体实现

对于方格道路，先用四邻接连接码识别直段、转角、T 型、十字和端头，再用四角/对角关系决定人行道收口。可用 shared-edge key 确保同一边只生成一次。

Dual Grid 将节点状态变成模块角点的配置，适合连续轮廓与转角。16/256 种配置仅针对二值情况；加入材质、用途、高度后组合数增多，应分解为“基础占据拓扑 + 边属性 + 结构规则”，而不是制作一张无限膨胀的全状态查表。

## 6. 动态更新与跨格部件管理

建议为每个生成特征记录：

```ts
// 设计草图，不是工程中现存接口。
type GeneratedFeature = {
  id: string;                 // 稳定结构/立面/窗间或共享边标识
  kind: 'window' | 'cornice' | 'sidewalk' | 'stairs';
  sourceNodes: string[];       // 生成依据
  occupiedBounds: Bounds;     // 可跨多个原格
  dependencyBounds: Bounds;   // 还读取了哪些空间/邻接关系
  addStamps: VoxelStamp[];
  subtractStamps: VoxelStamp[];
  walkConnections?: WalkLink[];
};
```

关键机制：

- 建立输入节点→特征的反向索引，以及空间查询。修改一个节点后，删除/重建依赖它或读取该空间的特征；再重建受影响的渲染块和碰撞/导航连接。
- 候选特征分阶段生成：结构占据与通道→入口/楼梯/平台→窗/檐口→花箱/植被。出现占据冲突时按稳定优先级解决，不能依赖遍历先后顺序。
- 窗口的 add/subtract 是一个整体，在确定的结构层内开洞，不能让另一个节点重建的墙又把洞填上；不要从已装饰的结果反向作为下一轮输入，防止重复叠加。
- 直段/转角一般局部更新；立面宽度变化、道路区域合并拆分可能影响整段结构。不能承诺每次最多只重算 3×3×3。
- 采用稳定建筑 ID、立面坐标系、规则版本和 seed。若要左右对称的窗列，扩建后允许整段重新排布；若要极强的局部稳定性，用固定窗间锚点。两种编辑风格应明确选择。
- 将“生成特征”与“渲染 chunk”分开：跨格窗台由一个 feature 拥有，几何可以分发到多个 mesh chunk。异步生成结果带输入版本，防止旧结果覆盖新编辑。

## 7. 当前工程缺什么、可以直接用什么

本轮只读核查得到：

- [粗材质表](/D:/tiangongtest/game/assets/voxel/model.ts:5) 仅表达 Grass、Dirt、Stone、Wood、Planks、Brick 等。它能支持几何邻接和材质判断，不能可靠区分石头道路与自然岩石。
- [建筑契约](/D:/tiangongtest/game/assets/colony/contracts.ts:9) 已有 wall、door、floor，可作为第一批语义输入。[建筑状态](/D:/tiangongtest/game/assets/colony/contracts.ts:39) 尚无朝向、楼层、样式、建筑分组或开窗意图。
- [房间格数据](/D:/tiangongtest/game/assets/colony/contracts.ts:45) 可辅助判断内外侧，但对开放墙段、隔墙和孤立墙仍可能有歧义。
- `path` 是居民的临时寻路数组，不是道路地图。现有 zone 只有农田和仓储；现有 floor 是室内木地板，不能默认全部解释成人行道。
- [当前建造占据](/D:/tiangongtest/game/assets/colony/simulation.ts:205) 按地表 `(x,z)` 判重，不支持墙与地板同格或任意多层建筑。窗台/窗框先作为墙的派生特征更合适；参考图那样多层楼的完整可玩结构属于进一步扩展。

最低新增源数据建议：道路/自然地表用途标记、建筑 styleId、必要的朝向/structureId、`opening=auto/solid/window/door` 覆盖。道路走向、路沿、转角与高度差由邻接推导，用户无需逐个摆放。

新增源数据应纳入现有存档 owner 和导入/导出校验，并为旧存档提供默认值；生成的窗台、路沿等可由版本和源数据重建，不必全部保存。仅保存纯视觉微格的旧方案不足以表达会影响导航的结构意图。

建议代码职责（尚未创建）：

```text
pcg/semantic-map.ts      粗格、建筑与用途标记的统一输入
pcg/topology.ts          邻接、共享边/角、立面/道路区域
pcg/facade-rules.ts      窗间、开洞、窗台、檐口、入口
pcg/road-rules.ts        路面、边界、人行道、路口、高差连接
pcg/feature-store.ts     特征ID、空间占据、依赖和增量失效
pcg/voxel-emitter.ts     1/16精度的模块/形状输出与布尔组合
pcg/mesh-output.ts       合并、AO、LOD与原生MeshAsset
```

无需一开始编写完整 CGA 解析器。第一轮可以用类型明确的 TypeScript 生成函数表达 split、repeat、extrude、reserve、carve、stamp 几种操作；规则验证稳定后再考虑数据化编辑器。

## 8. 先验证什么

第一轮应验证“修改源节点会改变结构”的闭环：

1. 墙从 3 格延长到 6 格，窗列数量/布局按规则变化，窗台确实向外凸出。
2. 墙转弯形成 L 形，内外角收口；被邻墙遮挡的窗候选取消。
3. 添加/移动入口时，窗台、平台和人行通道互相避让。
4. 一条路改成 T 型或十字路口，原接入口的路沿消失，外围人行道连续。
5. 两个不同高度的步行面，空间足够则生成台阶，空间不足则产生可解释的保守结果。
6. 重载与不同更新顺序得到同样结果，删除源节点不会残留悬空装饰；跨 chunk 的部件没有接缝和重复。
7. 角色能实际沿生成的通路行走；窗洞、玻璃和墙体的碰撞行为符合设定。

视觉目标与参考图对照时，优先看建筑整体比例、窗口节奏、檐口/入口层次和道路连续性。微体素噪声、砖纹、花草、AO 与照明是后续精修；达到参考图的艺术质量还需要一致的模块设计和场景构图，不能仅由一个邻接算法保证。
